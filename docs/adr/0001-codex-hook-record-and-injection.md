# Record Hooks Individually and Inject by Name

Codex hooks will be managed as individually named records. `record` accepts either the effective global layer or a specified directory, reads `~/.codex/hooks.json` or `<dir>/.codex/hooks.json`, and creates one record for each custom hook it finds. Each record is identified by the executable filename stem and lives in `codex-hooks/<hook-name>/` without the executable suffix; its `hook.json` contains only that hook's code metadata, registrations, and source marker. The first version supports only custom `command` handlers. A record is injected by hook name into Codex's global `~/.codex` layer or the exact directory supplied as the local target.

This boundary deliberately separates hook definition from record source and injection target: a single named hook is managed independently, rather than exporting or injecting an entire directory at once. Codex continues to own event matching, trust, and layer-merging behavior.

Recording scans one supported source layer at a time and stores every custom hook as an independent record, excluding registrations belonging to other hooks. Records from a directory keep the Git origin URL as their source marker, falling back to the directory name when no origin exists; records from the user layer are marked global. Injection selects one record by hook name, copies its executable to `<target>/codex-hooks/<hookfile>`, and merges only that record's registrations at their original events and matchers into `<target>/.codex/hooks.json` (or `~/.codex/hooks.json` for global injection), preserving unrelated hooks. An existing same-name record or target hook is rejected unless `-f` is explicitly provided. The CLI exposes only `record` and `inject`; inline `[hooks]` TOML is outside the scope. Hook trust and review remain Codex responsibilities.
