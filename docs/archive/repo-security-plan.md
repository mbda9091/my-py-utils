## 2. 范围

### 2.1 目标

- G1：用户输入已有 Git 仓库路径，一条命令完成配置、锁定依赖安装、工具可用性验证和本地 hooks 启用。
- G2：预览不产生写入；重复接入不覆盖自定义内容；冲突和安装失败可诊断、可恢复，不误报接入成功。
- G3：提交检查实际暂存快照，推送检查新引入的各个提交；命中风险或工具失败均阻止操作，输出不包含命中的原文。
- G4：可检查安装健康度，主动扫描暂存区、HEAD 或本地可达历史，并按需生成 GitHub Actions 工作流。
- G5：工具能够通过独立 wheel 和聚合安装包分发；目标项目不必添加扫描器到自身业务依赖，也不依赖原模板所在的机器路径。

### 2.2 非目标与延期项

| 事项 | 本轮处理 | 原因或后续触发条件 |
|---|---|---|
| IDE、浏览器、AI 编码助手扩展 | 不做 | 本轮“插件”指扫描组件及 Git hooks |
| 自动串联 Husky、pre-commit 或任意既有 hook | 延期 | 执行顺序、工作目录及 pre-push 标准输入传递需单独设计 |
| GitHub Push Protection、分支保护、组织策略 | 不自动修改 | 需要远端权限与独立配置；仅给人工说明 |
| 自动修复代码、轮换密钥、清洗 Git 历史 | 不做 | 扫描结果由用户审查处理 |
| 自动下载云端规则、按语言扩充漏洞库 | 延期 | 首版固定本地规则；其他语言规则需明确评审与验收 |
| 默认全历史扫描、自动 fetch、自动建立忽略基线 | 不做 | 历史成本不可预估；不擅自扩大网络操作或缩小检查范围 |

| 自动升级、卸载命令、批量接入多仓库 | 延期 | 首版提供冲突诊断与人工回退；版本清单为后续升级提供依据 |
| 自动提交、推送、发布 CLI 或触发真实远端 CI | 不包含在本轮自动操作中 | 本轮生成配置并本地验证；实际发布和目标仓库提交另行执行 |

### 2.3 适用场景与协作边界

- 目标为用户信任、可写的普通非 bare Git 仓库。接受仓库根目录或其内部目录，统一定位并显示真实根目录；不向上误用仓库外路径。
- 本轮支持 Linux x64，实测环境为 Ubuntu 22.04.5 用户态、glibc 2.35、WSL2 Linux 内核及本地 Linux 文件系统。macOS 原生验收由用户明确延期；Linux arm64、原生 Windows 和 Windows 挂载盘未验收。保留其他平台的下载摘要不构成支持声明。
- CLI 自身遵循本仓库 Python 3.11+ 约定。参考模板扫描依赖限定 Python 3.11–3.13，拟为独立扫描环境选定 Python 3.13，由 uv 管理，不强迫目标项目修改 Python 版本。
- 首次安装需要 Git、uv 和联网；正常本地扫描使用已安装工具及本地规则。setup 可由 uv 获取所需 Python 和依赖，需在预览中说明下载与磁盘写入。
- 工具对目标仓库配置负责；目标仓库的源码、暂存区、提交、远端设置由用户管理。不会将待提交配置自动暂存。
- 完成定义：以用户最新确认的 Linux x64 范围满足 M1–M3、A1–A12，完成真实单包/聚合 wheel 验收及实现提交/产物摘要对账。macOS 明确延期，不作为本轮必需项；未测平台不声称通过。目标仓库真实 GitHub CI 仍为条件性验收。

## 4. 具体方案

本节为完整首版的当前有效设计。M2 的本地功能已实现，当前接口见第 4.3 节；平台与分发形态仍按第 8 节逐项记录，不推断未测环境通过。

### 4.1 总体设计与职责

采用“薄 CLI + 接入规划/执行 + 随包模板”的结构。CLI 运行依赖不包含三个重量级扫描器；扫描器安装在目标仓库 `.security/.venv/` 和 `.security/bin/`，不进入目标项目的业务环境。

| 部分 | 职责 | 输入与输出 | 本轮改动 |
|---|---|---|---|
| `packages/repo-security/pyproject.toml` | 包元数据、`repo-security` 命令、模板资源打包 | 构建配置 → 独立 wheel | M1 已新增 |
| `src/repo_security/main.py` | 参数解析、用户输出、退出码 | 命令 → 服务调用与结果 | 已有 setup/dry-run/doctor/scan 与 CI 选项 |
| 包内规划、安装和诊断模块 | 仓库预检、冲突分析、文件部署、工具安装、健康检查 | 路径/选项 → 计划、执行结果或诊断 | M2 已有共享 typed `templates/manage.py`；core 负责资源交接 |
| 包内模板资源 | 运行脚本、本地规则、锁文件、hooks、CI 模板 | 固定发布资源 → 目标仓库文件 | M2 已有可选 CI 生成，所有 Action 固定 SHA |
| 目标 `.security/` | 独立扫描运行时和规则 | Git 对象 → 脱敏结果 | M1 已可生成；目录结构沿用模板 |
| 目标 `.security/install-manifest.json` | 工具及模板版本、受管文件路径/摘要、安装阶段、hooks 原值 | 安装过程 → 可重复诊断的状态 | M2 已有；不含用户名、绝对机器路径或凭据 |
| `tests/test_repo_security*.py` | 安装行为、扫描语义、故障注入 | 临时仓库和合成数据 → 验收证据 | M2 共 51 项通过；真实扫描器依赖由环境变量显式提供 |
| workspace、聚合包和 README | 依赖、来源、命令和使用说明注册 | 新包 → 单包及聚合安装均可调用 | M1 已注册；M3 Linux 单包/聚合四组合均已验收 |

### 4.2 关键行为与异常路径

#### 4.2.1 预检与只读计划

1. 规范化输入并定位根目录，校验仓库类型、可写性、平台、Git/uv 和目标路径类型；不要求业务工作区干净。
2. 检查实际生效的 `core.hooksPath` 及其配置来源，覆盖 local/global 等层次；检查原 hooks 目录中的 pre-commit/pre-push。遇到第三方 hooks 时在任何目标文件写入或下载前失败，说明冲突位置及人工接入命令。
3. 检查所有拟写入对象；受管文件及目录不得通过符号链接写到仓库外；规则等读取入口的符号链接也视为冲突。保留无关文件。
4. 输出新增、保持、冲突的相对路径，Git 配置变化、下载内容和安装 Python 的可能性。`--dry-run` 到此结束：不写文件、不 chmod、不修改 Git 配置，不下载、不建立虚拟环境。
5. 即使预检通过，实际写入及启用 hooks 前仍复核相关状态；同仓库并发 setup 通过排他锁拒绝第二个写入进程，异常遗留锁报告人工恢复方法，不盲目抢占。

#### 4.2.2 部署、安装和启用顺序

1. 按发布时明确的资源清单部署文件，不递归复制参考目录。保留 `.gitignore` 原有内容，仅补充缺失的定向忽略项，不追加全仓 `__pycache__/` 等无关策略。
2. 调用随模板提供的独立安装入口，通过 uv 在 `.security/` 同步锁定依赖，并显式选择扫描器 Python 版本，避免继承业务项目的 Python 要求。
3. Gitleaks 下载须通过预置 SHA-256；临时下载后校验再发布到最终路径。已有二进制也要核验版本及与校验过安装记录一致的摘要，无法证明可信时重新获取校验通过的发行包，不仅检查文件存在。
4. 验证扫描器版本、可执行权限、规则可加载及合成样本检测。不扫描用户业务代码作为安装健康度判断，避免现有风险与安装失败混淆。
5. 所有文件和依赖就绪后，才设置仓库级 `core.hooksPath=.security/hooks`。不改全局配置；复核实际生效值后，将清单状态标记为 ready。
6. 输出配置成功和扫描覆盖边界，提示用户审查生成文件、执行首次历史审计。setup 不自动扫描历史、不 fetch、不提交。

下载和构建依赖仅针对本工具固定的扫描环境；不得运行目标项目的构建、测试或业务安装脚本。uv 自身缓存和 Python 安装可能写入用户缓存目录，应与目标仓库写入分别说明。

#### 4.2.3 幂等、冲突和失败恢复

- 相同版本和相同内容不改写；`.gitignore` 不重复追加；仅当健康检查通过且 hooks 生效时返回成功。已安装依赖可校验复用，不承诺修复缺失环境时完全离线。
- 有安装清单时区分发布原始摘要、已安装摘要及当前文件内容；无清单时仅自动认领与当前发布模板完全一致的文件。所有计划内文件冲突一次汇总，在写入前报错。
- 自定义规则、其他版本资源和同名自定义工作流不覆盖；首版无 `--force` 和自动升级。可保留用户规则做 doctor/scan，但 setup 遇到不同内容给出人工对齐指引。
- 初次接入若安装或验证失败，不启用新 hooks；保留已落地的完整模板和 incomplete 清单供重试，清理未完成的临时文件。提示哪些文件、忽略项和缓存已产生，不能声称全部回滚。
- 原安装已启用 hooks 时，失败修复不主动禁用保护；运行时工具缺失继续返回错误并阻止操作。
- 若启用 Git 配置后复核失败，在确认配置仍为本次写入值时恢复原本的 local 值；原 local 未设置则 unset 本次值，让继承配置恢复。遇到并发改变不覆盖，报告待人工处理状态。
- 普通重试只补齐同版本且未被改动的安装。进程中断后通过清单与实际文件、Git 配置交叉判断；清单不是文件可信度或安装成功的唯一依据。

#### 4.2.4 扫描与诊断契约

- pre-commit 检查整个暂存快照，包含部分暂存时的实际提交版本；不临时 stash，不修改索引或工作区。
- pre-push 保留 Git 传入的 ref 更新标准输入，覆盖每次更新新引入的提交及中间提交；首次推送或旧对象不可用时沿用模板的完整祖先检查；删除 ref 跳过。
- 手动 `scan` 支持 staged、head、history，默认 staged。history 仅覆盖本地引用可达历史，不自动 fetch；浅克隆显示覆盖不足，不能称为完整审计。
- 任一命中返回 1；工具缺失、配置错误、超时或报告异常返回 2，两者都拦截。输出文件、行号及规则类型，不转发扫描器原始 stdout/stderr 或匹配内容。
- doctor 只读检查文件完整性/定制差异、安装状态、实际工具版本、hooks 路径及权限、运行时可用性、CI 是否存在；不自动安装、修复或扫描业务历史。用隔离合成样本校验工具的行为时仅写私有临时目录，退出后清理。
- 二进制、非支持编码、子模块、大文件等行为沿用参考模板并明确报告；不自动添加白名单，不放宽本地规则或扫描错误策略。
- hooks 可被用户绕过，本地扫描结果不等于完整安全审计；GitHub CI 在上传后执行，不能撤回首次泄露。

### 4.3 接口、配置与使用方式

以下命令均为 **M2 已实现接口**。`setup` 支持同版本重试/认领；`--dry-run`、`--github-actions`、`doctor` 均可用。CLI 可从任意目录执行，显式传仓库路径，含空格时由调用方引用。版本为 0.2.0，不自动升级 M1 的旧模板。

```bash
# 仅查看计划：不写目标或安装工具
repo-security setup /path/to/repo --dry-run

# 默认接入：部署、安装、验证，然后启用本地 hooks
repo-security setup /path/to/repo

# 同时生成可选 GitHub Actions 工作流
repo-security setup /path/to/repo --github-actions

# 只读诊断；业务文件不作为健康检查样本
repo-security doctor /path/to/repo

# 扫描 Git 对象；省略 mode 时默认 staged
repo-security scan /path/to/repo --mode staged
repo-security scan /path/to/repo --mode head
repo-security scan /path/to/repo --mode history
```

保留模板的 `.security/run staged|head|history` 和 `python3 .security/setup.py --install-hooks` 独立入口，使生成结果在新 clone 中不强依赖 repo-security CLI。安装器必须使用与外层一致的依赖验证和 hooks 冲突检查；它负责重建本机环境，不承担模板升级。文档分别列出两种入口的适用场景。

统一退出码：0 为操作成功或诊断健康；scan 的 1 为风险命中；其他命令的 1 为健康检查未满足；2 为参数、环境、冲突或执行错误。dry-run 存在冲突返回 2，同时展示完整计划；不会将“可预览”算作“可安装”。

已有模板配置文件保持原职责：`gitleaks.toml` 管凭据规则，`semgrep.yml` 管代码规则，`policy.json` 管 PII 例外、自定义 pattern、大小上限及排除路径。不新增自动语言推断或自动放宽规则。生成包内 README 说明配置变更需审查及哪些内容应提交。

可选工作流固定使用 `.github/workflows/repo-security.yml`，同名且内容不同则冲突；不重写其他工作流。保持只读 contents 权限、完整历史 checkout、不持久化 checkout 凭据，固定运行 Python/uv 版本并采用经审查的 Action 提交 SHA。仅生成 YAML 不代表远端已启用必需检查。

### 4.4 兼容、迁移与回退

- 现有 CLI 行为不变；新包按仓库规范加入聚合依赖、sources、scripts 和命令清单，依赖变更使用 uv 并提交锁文件。
- 扫描脚本、规则、锁文件和 hooks 一同作为发布资源管理，包构建不得带入 `.venv/`、`bin/`、缓存或机器路径。通过 `importlib.resources` 访问资源，不要求源码 checkout。
- 已手工接入原模板的仓库：先运行 dry-run；与发布模板一致的文件可认领，定制内容及版本差异报告冲突。首版不承诺迁移所有旧模板版本。
- 默认 hooks 依赖本机安装；配置文件提交后，新 clone 仍需运行 setup。自定义规则可由用户编辑并用于扫描，doctor 显示偏离默认；不会仅因定制差异就判定存在漏洞。
- 首版人工回退：停止并发操作，依据清单恢复本仓库原 local hooksPath；仅当当前值仍由本工具管理时恢复。无原 local 值则移除本次 local 值，不修改 global。修改过的受管文件及 `.gitignore` 由用户对照 diff 处理，不提供递归自动删除。
- 本机 `.venv/`、`bin/` 可在停用本工具 hooks 后由用户删除；不删除 uv 共享缓存。已经提交的模板通过正常 Git 提交流程回退，不重写历史。单纯停用 hooks 不表示风险已解决。
