## 1. 结论摘要

- **要解决的问题**：当前工具把技能纳管、安装与 Git 发布绑定在一起，维护技能需要理解缓存仓库和 publish；这偏离了用户直接维护个人技能 Git 仓库的工作方式。
- **采用的方案**：用户配置一次独立的个人技能仓库目录并持久保存，后续命令直接复用；只支持绑定一个仓库。真实文件放在该仓库的 `skills/` 下，客户端使用目录通过软链接引用。Git 暂存、提交、拉取和推送由用户自行执行。
- **本轮边界**：保留本地配置、add、install、list、status、validate；拟移除 publish、sync 和工具设置 Git 身份的行为。只管理个人仓库及明确登记的使用入口。
- **当前进展**：M1 已实现并完成 Linux 本机功能验收：109 项包内测试、静态检查、类型检查和全部包构建通过。配置 v2、单仓库持久复用及纯 SKILL.md 发现可用；尚无实现提交 SHA，不能标整体已完成。
- **下一步**：进入 M2，解除 add/install 的远端、分支、提交和发布元数据依赖，落实安装记录迁移与冲突保护；M3 再移除旧发布路径。详见第 5、10 节。

## 2. 范围

### 2.1 目标

- G1：用户能够将一个位于客户端使用目录之外的本地 Git 仓库持久配置为唯一的个人技能仓库；后续调用无需重复指定路径，重启终端或改变当前工作目录仍复用该配置。
- G2：用户能够通过 `add` 将指定技能移入个人仓库，并在原位置保留指向真实内容的软链接。
- G3：用户能够通过 `install` 安装仓库中的技能；经软链接编辑后，变化直接落在个人仓库，能够用原生 Git 查看、暂存和提交。
- G4：纳管和安装能够保护原始内容、明确报告冲突，只影响用户指定的技能和已登记的个人技能入口。
- G5：工具的正常工作不依赖远端、Git 身份、固定分支、已有提交或干净工作区，也不会自动执行 Git 写操作或网络操作。

### 2.2 非目标与延期项

| 事项 | 本轮处理 | 原因或后续触发条件 |
|---|---|---|
| Git init、clone、add、commit、pull、push、分支切换及身份设置 | 由用户执行 | 用户已明确要求自己维护 Git 工作流 |
| 将客户端使用目录整体建为 Git 仓库 | 不采用 | 其中包含其他来源技能，不能等同于个人技能归属 |
| 自动吸收使用目录下的所有技能 | 不提供 | add 必须由用户明确指定来源目录 |
| 插件市场、第三方技能升级与卸载 | 不管理 | 不属于个人技能仓库的职责 |
| 多个个人仓库同时管理、命名仓库配置与每次调用选择仓库 | 不支持 | 用户已确认只绑定一个仓库目录，日常命令统一复用配置 |
| 项目级安装、多客户端目标 | 延期 | 本轮保留已有 Codex 用户级安装目标 |
| 自动合并同名技能、自动恢复历史版本 | 不提供 | 内容取舍与版本回退交给用户和 Git |
| 自动提交前隐私检查或自动安装 Git hooks | 不接入 | 移除 publish 后工具不位于 Git 提交链路；既有独立仓库安全工具可由用户自行配置 |

### 2.3 适用场景与协作边界

- 适用对象：用户自行维护的 Skill；第三方技能只有在用户明确通过 add 选择纳管后，才进入工具管理范围。
- 环境范围：Python 3.11+；本轮必需验收环境为支持目录软链接的 Linux。macOS 按实际使用需要追加验证，不能继承 Linux 结论；Windows 链接权限和运行体验暂不承诺。
- 内容归属由个人仓库决定；使用入口由软链接及安装记录描述；Git 历史由用户维护。安装记录不是内容的第二份清单。
- 完成定义：第 4.5 节 A1–A10 全部通过；职责一致的文档和包构建完成；第 5、8、9 节补齐实现 SHA、验收基线与报告。真实个人环境的迁移只在用户实际执行后记录为人工验收，临时目录测试不代替该结果。

## 4. 具体方案

### 4.1 总体设计与职责

目录示例为目标布局，路径使用占位符。M1 已支持个人仓库绑定与发现；使用目录的链接迁移仍待 M2。

```text
<personal-skills-repo>/           用户指定的 Git 工作仓库
  .git/                          普通仓库；Git worktree 的 .git 文件也应支持
  skills/
    foo/
      SKILL.md
      scripts/
    bar/
      SKILL.md

<agent-skills-dir>/              Codex 默认使用 ~/.agents/skills
  foo -> <personal-skills-repo>/skills/foo
  vendor-skill/                  其他来源，工具不纳管

<skill-sync-state>/              默认 ~/.skill-sync，仅保存本机配置与安装记录
  config.json
  installations.json
```

技能使用目录与个人技能仓库必须分离，二者不能相同或互相包含。校验规范化后的实际路径，防止通过父目录软链接绕过。状态目录也不能被选为整个个人技能仓库；旧状态目录下的 `repository/` 可作为兼容过渡位置，不再具有“缓存可随时删除”的语义。

| 部分 | 职责 | 输入与输出 | 本轮改动 |
|---|---|---|---|
| repository/config | 绑定本地个人仓库，保存本机配置 | 本地路径 → v2 配置；不保存远端、分支或 Git 身份 | M1 已实现；v1 原件和旧记录备份保留，记录转换待 M2 |
| catalog/validation | 从 `skills/*/SKILL.md` 识别、校验个人技能 | 真实目录 → 名称、描述、路径 | M1 本地发现已实现；旧安装调用待 M2 改造 |
| adder | 将明确指定的外部目录纳管并反向链接 | 本地目录 → 仓库真实目录与原路径软链接 | 复用回滚，移除发布依赖 |
| installer/links | 为仓库技能建立使用入口，保护冲突路径 | 技能名称 → 软链接与安装记录 | 修改覆盖规则和所有权判断 |
| status/list | 只读展示仓库技能与已登记入口状态 | 配置、技能、记录 → 状态文本 | 修改；不枚举其他来源技能作为管理对象 |
| Git 只读适配 | 确认用户绑定的是工作仓库，提供可选状态信息 | 本地工作仓库 → 根目录、状态 | 收缩；无 origin、身份、分支限制 |
| publish/sync | 不再承担产品职责 | 旧命令 → 明确的迁移提示或用法错误 | 移除可执行行为及专用代码、测试 |

Git 只读信息获取应兼容尚无 HEAD 的仓库，并关闭可选锁，避免 status 等读取隐式刷新索引。工具不执行 `git add`，因此“纳管成功”只表示文件归入个人仓库；新文件在 Git 中通常仍是 untracked，由用户自行暂存。

### 4.2 关键行为与异常路径

#### 4.2.1 绑定本地仓库

M1 已将 `init --repo` 调整为显式绑定本地路径：校验该路径是 Git 工作仓库根目录，检查与使用目录分离，再原子写入配置。用户可以先自行 git init 或 clone；工具不代做。无远端、无首次提交、dirty 工作区或切换了分支，不妨碍已交付的配置和发现；add/install 解除这些依赖仍待 M2。

绑定结果持久保存，配置只容纳一个仓库目录。后续 add、install、list、status 自动读取该目录，不接收仓库选择参数，也不根据当前工作目录重新推断或重复询问。未配置时提示先配置；已配置的目录失效时报告路径问题，不能悄悄改用其他目录。再次绑定相同目录幂等；显式配置不同目录表示替换唯一绑定，按第 4.4 节迁移，不保留多个可选仓库。

已有 `skills/` 时保留；不存在时创建空目录。它及其技能一级目录必须是真实目录，不允许通过软链接把内容来源扩展到个人仓库外。个人仓库损坏、路径失效、SKILL.md 无效时，报告具体路径，不自动另建仓库或修复 Git 状态。

#### 4.2.2 add 纳管

1. 读取配置，校验输入是用户明确选定的合法技能目录，名称与 SKILL.md frontmatter 一致。
2. 若输入已经是仓库中的该技能，或是指向同一技能的软链接，返回“已纳管”；仓库内的真实目录不创建指向自身的链接。
3. 普通外部目录以 `<repo>/skills/<name>` 为目标。仓库同名项存在时拒绝，保留双方内容；不提供 add 强制合并或覆盖。
4. 预读安装记录后，将内容准备到仓库侧临时目录；验证准备结果，再备份原目录、落位真实目录、在原位置建软链接，并写入安装记录。
5. 全部成功后才清理原目录备份。中途失败恢复原目录并清理本次临时副本；恢复失败则保留备份，输出可恢复位置，不删除原始数据。

纳管保留技能内容，不生成或刷新 `skill-sync.json`；不按旧 publish 过滤规则删除用户文件。跨文件系统使用复制准备与原目录备份，不能先删原文件再尝试建链接。复制后、替换前须检测源目录是否发生修改；发现变化则终止，避免迁移时丢失并行编辑。命令输出提示迁移完成前停止编辑该技能。

外部软链接指向其他位置时拒绝，避免悄悄转移其真实目标。来源目录包含其他 Git 仓库或 worktree 元数据时先拒绝并保留原件，提示用户自行整理仓库边界，防止手动 git add 后产生意外子模块；它不属于需要自动删除的临时文件。

#### 4.2.3 install 安装及冲突保护

安装从配置的个人仓库查找技能，默认目标为 `~/.agents/skills/<name>`，创建指向真实技能目录的绝对软链接。已有 `install --all` 仍仅遍历个人仓库中的技能。

| 目标位置现状 | 拟采用行为 |
|---|---|
| 不存在 | 创建链接并登记；失败清理本次链接 |
| 已指向同一技能 | 幂等成功；必要时补齐安装记录 |
| 已登记、链接目标仍与记录一致，但需从旧个人仓库迁至新仓库 | 仅显式 `--force` 可重新链接；不删除旧内容 |
| 实体目录、普通文件、指向其他来源的链接，或来源无法确认的断链 | 冲突并保留；即使传 `--force` 也不直接覆盖 |
| 记录说是工具安装，但实际目标已被人工替换 | 以实际内容为准，报告冲突；不以旧记录作为删除授权 |

这是对当前 `--force` 的收紧：它仅允许修复可核对的个人安装关系，不再用于删除未知内容。使用目录内的其他来源技能不会因为执行 install、install --all 或 status 被吸收或清理。批量安装遇到冲突可继续其他项，最终汇总失败并返回非零退出码，避免把部分失败显示成全部成功。

#### 4.2.4 日常编辑与手动 Git

经原路径修改 Skill，修改的就是个人仓库真实文件。工具不设置提交身份、不暂存文件、不创建提交、不切换分支，也不自动拉取、推送或重试 Git 合并。

用户自行选择检查、暂存和提交的文件。仓库切分支、git pull 或删除技能后，使用入口直接反映工作目录当前状态；status 对已登记断链给出提示，工具不自动恢复文件或更改 Git 状态。

#### 4.2.5 list、status 与 validate

- list（M1 已实现）：只读扫描配置仓库的 `skills/`，输出名称、描述和真实路径；从 SKILL.md 获取信息，不要求额外发布清单。
- status（M1 已实现）：显示个人仓库位置、配置路径及技能数量。M2 再增加已登记使用入口及正常/缺失/断链/被替换状态，仅核查已登记路径，不把整个使用目录当作个人资产清单。
- validate（M1 已实现）：保留技能结构校验，输出“结构有效”等与本地纳管一致的措辞，移除“可以发布”的含义。
- 不再维护发布时刻、兼容性固定数组及安装 commit 锁定含义。Git 状态作为辅助信息，不能成为 add/install 成功的前置条件。

```json
}
```

`repositoryPath` 是单个路径字段，保存规范化后的绝对本机路径；不引入仓库列表、仓库名称或当前仓库切换机制。仓库根路径仅在首次配置或显式更换绑定时提供，日常 add、install、list、status 不再传 `--repo`。`SKILL_SYNC_HOME` 与默认本机状态目录继续有效，但只影响本机配置和记录的存储位置，不作为产品中的多仓库配置入口，也不根据调用位置决定技能仓库。

拟调整安装记录为按完整使用路径区分的 schema v2：每条记录保存技能名、使用路径、创建链接时的真实来源路径，以及可识别的客户端目标；任意路径 add 的入口标为本地路径，不假定都是 Codex。单个技能可有多个记录；仓库中的技能存在与否仍由技能目录决定。

当前 installations.json 是没有版本字段的记录字典；迁移须单独识别这个旧格式，不能直接按带 schemaVersion 的新结构读取。

#### 目标流程示例

以下包含已交付的 init/list/status 及待 M2 实施的 add/install，分别在注释中标明。Git 命令由用户手动执行，工具命令通过工作区运行器调用；已安装 CLI 时可直接使用 skill-sync。

```bash
# 用户先准备或克隆自己的技能仓库；已有仓库可跳过 git init。
git init <personal-skills-repo>

# M1 已可用：首次配置唯一仓库，持久保存。
uv run --package skill-sync skill-sync init --repo <personal-skills-repo>

# M1 已可用：后续调用自动复用配置，不再指定仓库目录。
uv run --package skill-sync skill-sync list
uv run --package skill-sync skill-sync status

# 待 M2：吸收本地技能，仍复用上述配置。
uv run --package skill-sync skill-sync add <agent-skills-dir>/foo

# 用户照常编辑原路径。随后在个人仓库中自行检查和提交。
```

### 4.4 兼容、迁移与回退

- **旧配置（M1 已实现）**：识别 schema v1，不把旧 repository URL 解释成本地路径。只读状态提供迁移说明；通过显式 `init --repo` 转换为 v2 时，先备份旧配置和安装记录，不自动搬动 checkout、重写链接或访问网络。旧安装记录文件保持原样，其数据结构转换待 M2。
- **旧技能内容**：`skill-sync.json` 不再是发现前提；已有文件先保留且忽略，不因绑定或安装自动删除。原仓库已有 `.gitignore` 和 Git 配置也保持原样。
- **旧安装记录**：将历史 commit 视为旧信息，转换为完整使用路径记录；从旧 checkout 和技能名还原来源路径。不能还原或与实际链接不符的条目标为待处理，不作为强制替换依据。
- **仓库迁移顺序**：用户先用自己的 Git/文件系统流程准备新位置并核对内容；工具备份并切换绑定；核查旧记录中的每个入口；Codex 标准路径可按已确认来源执行 install --force，任意原始路径由用户依据 status 清单手动重建链接；所有入口验证后，用户再决定如何处理旧仓库。
- **来源冲突**：实际入口指向第三方位置、实体目录或内容不一致时不自动合并；保留现场，由用户比较处理。迁移进度不能只看新配置是否写入成功。
- **回退**：新绑定失败时保持旧配置有效；迁移后需回退时，由用户恢复备份配置并将已改动的入口指回保留的旧仓库。绑定过程不清理旧仓库，因此仍有可核对来源。已经迁移后的新编辑需要用户自行比对，不承诺无条件自动合并。

原有工作区试实现保留为改造基线；M1 在该基础上交付本地配置与发现，不回滚既有改动，也未对任何真实个人技能执行迁移。
